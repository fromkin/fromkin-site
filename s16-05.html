Fromkin · 翻墙原理

第四章 墙的第二招：封IP与掐连接

地址抄在手里，还是进不了门

上一章末尾留了个问题：有人事先拿到了真地址，绕开了问路环节的抢答，怎么办？

这种情况每天都在发生。梯子软件不需要问路，它的节点地址本来就写在配置里；有些用户也会把常用网站的地址背下来、存下来。面对这批"不问路的人"，第一招是空的。于是墙亮出第二招，这一招的思路非常直接：不跟你绕弯子了，我认门牌号。你要去的那栋楼，整栋封掉；你正在打的那通电话，我当着你俩的面掐了。

这一招实际上是两个动作的组合：一个叫**封 IP**，对付的是"还没开始"的连接；一个叫**掐连接**，对付的是"已经开始"的通话。它们的性格不同：封 IP 简单粗暴，像一份贴在关口的通缉名单；掐连接则要阴险得多，它得冒充通信的一方来说谎。一个一个看。

封 IP：按门牌号封门

封 IP 的原理，一句话就能说完：在边界的关口上放一份黑名单，你的数据包要去的地址如果榜上有名，就在此止步，不放出境；从那个地址回来的包，也一样扣下。

名单上的地址从哪来？一部分是人工和规则维护的已知目标：某些网站的服务器、已知的梯子节点。而名单最大的来源，其实就是梯子自己：一个节点一旦被很多人使用，它的存在就不再是秘密——研究者能找到它，封锁方也能找到它。这也是为什么前言里说，免费节点的短命几乎是注定的：它的地址等于公开广播，封掉它没有侦查成本，只剩下一个"加入名单"的动作。

封 IP 的好处是稳：一旦名单生效，不依赖竞速、不依赖运气，十次访问十次失败，给人一种"此路不通"的确定性。但它的短板和它的好处一样明显。

**第一，地址是会跑的。** 服务器可以换地址，云厂商的地址池更是成千上万地轮换。封掉一个旧地址，对方搬个家就回来了，所以封 IP 是一场需要不断更新名单的追赶战，而不是一劳永逸的封印。

**第二，也是更要命的：误伤。** 如今的互联网高度"合租化"：一台云服务器上可能挤着成百上千个互不相干的网站，一个大公司的地址段后面可能站着邮件、云盘、办公系统和游戏服务。封一个 IP，常常等于封了一整栋合租楼。更极端的是内容分发网络，全世界无数网站共用同一批入口地址，封它们一个，等于误伤一片正当业务。第一章讲的成本账在这里具体化了：封 IP 每封一个地址，名单的维护者都要掂量一句——这一板子下去，会打中多少不相干的人。这个顾虑反过来成了很多服务的护身符：把自己的服务放到大平台的地址后面，封锁方投鼠忌器，这层心思，后面讲伪装时还会再出现。

**第三，封的粒度进退两难。** 一个一个地址地封，追赶不上对方换地址的速度；一整段一整段地封，又会把同一段里的正常服务成片扫倒。名单维护者永远要在这两个极端之间选一个刻度，而这个刻度选在哪里，又会反过来塑造市场的形状：刻度细，小节点活得久，靠换地址打游击的服务层出不穷；刻度粗，大平台被迫把服务拆得更散，或者干脆退出某些地址段。所以你会发现，封锁的"手感"在不同年份是不一样的，有时精细得像手术刀，有时粗放得像渔网——那不是技术忽高忽低，而是刻度在被反复调整。而每调整一次，两边的生态就跟着重新洗一次牌。

掐连接：伪造一张"对方已挂断"的条子

封 IP 管的是还没出门的流量。可有些连接的目的地不在名单上，却也不能让它好好说话——比如你正在访问的网站本身没被列入封禁，但你这次访问的内容、或者你使用的通道让守关口的人不满意。这时候，就需要能在通话进行中下手的办法。

回忆第二章讲的 TCP。它像打电话：接通靠握手，维持靠双方不断确认"我们说到第几句了"，结束则要有一方发出"挂断"的信号。在数据包的世界里，这个挂断信号就是一个带着 RST 标志的特殊包——相当于通话中突然塞进来的一张条子："对方已挂断，通话结束。"

问题来了：这张条子是谁都能伪造的。TCP 的设计里，收到 RST 的一方，出于礼貌和效率，会立刻相信并拆线，它没有余力去验证这张条子到底是对方写的，还是路边的人冒充的。于是守在边界的那只"手"就有了一件趁手的兵器：它盯着来往的流量，一旦决定要掐断某通对话，就同时向通信双方各注入一张伪造的 RST 条子——给你一张，冒充服务器写的；给服务器一张，冒充你写的。两边都以为是对方先挂的电话，各自收线走人。一场通话，就这样被中间人当面搅黄。

你的体感是什么？网页加载到一半突然中断，浏览器报出"连接被重置"的错误；或者一个长连接莫名其妙地断开，重连又能用一会儿。公开研究很早就记录过这种手法：从境内访问某些境外内容时，连接会在毫无征兆的情况下被 RST 打断，而且打断的时机和所访问的内容有关。

这里正好补一段历史。在互联网的上古时期，网页大多是不加密的，内容在路上明文可见。那时候，守关口的人有一种更精细的玩法：不看地址看内容，你传的东西里出现了名单上的关键词，就立刻注入 RST 掐断。这就是"关键词过滤"的经典形态——按词掐线。它后来式微，原因不是守关口的人手软了，而是 HTTPS 普及了：内容被锁进保险箱，这双手再也看不见词了。这一段历史很重要，它标出了整场攻防的一条主线：加密的每一次普及，都会废掉墙的一批旧招，同时逼它把重心移向"不需要看内容"的招式。这一章剩下的 SNI 阻断，和下一章的深度检测，都是这样被逼出来的。

SNI：信封封面上，还有一行字没藏好

内容看不见了，那就看目的地。可在加密时代，"目的地"这个信息的藏身之处，变得有点尴尬。

设想你要访问一个加密网站。内容还没开始传，先要走一遍加密握手：双方打招呼、验明身份、商量暗号（第六章细讲）。这遍握手里有一个设计上的无奈：你的浏览器必须在第一句话里就报出自己想找的网站名字。因为很多服务器是"合租"的——一个地址后面住着几十个网站，服务器得先知道你找谁，才能拿出对应的证书来接头。这个报名字的动作，名字叫 SNI，它就像信封封面上的收件人姓名：信的内容锁在里面，封面这行字却印在明处。

守关口的人要的正是这行字。它看不见你的信，但它低头一瞥封面，就知道你要和哪个被禁的网站通信。接下来它要做的，就是刚刚讲过的那套动作：在连接还没真正建立起来时，注入 RST，把通话掐死在摇篮里。

SNI 阻断和封 IP 都针对目的地，但手感不同，值得分清。封 IP 封的是地址：粗，一封一整片，容易误伤合租户。SNI 阻断封的是名字：细，同一个地址上的几十个网站，它能只掐其中一个，其他的照常放行。对于封锁方，这显然是更精细、成本更低的工具——也解释了一个常见现象：某些大平台你打开它的主页没问题，点进它旗下某个具体的服务就断，那未必是对方服务器的故障，而可能是掐线的粒度细到了"名字"这一层。

当然，这一招也有它正在被填补的漏洞。既然病根是"封面上的字没藏好"，思路自然是把封面也加密——让握手的第一句话都不露名字。这正是 ECH（加密客户端问候）这个新技术在做的事，它是 SNI 的加密升级版。目前它还在逐步部署的过程中，浏览器和大网站在陆续支持；它全面铺开的那一天，按名字掐线就会像关键词过滤一样，大批失效。至于那一天还有多远、墙会拿什么来接这一招，属于分析推演的范畴：可以确定的是，攻防双方都已经盯上了这块封面，新一轮的较劲正在这里集结。

这一招的共同前提：目的地必须看得见

把封 IP、RST、SNI 三件事摆在一起，会浮现出一个共同点：**它们全都依赖"看得见目的地"**。封 IP 要看到地址，SNI 阻断要看到封面上的名字，注入 RST 也得先确认这通电话打给了谁。换句话说，这一整招的动眼不动手——它不关心你说了什么，它只关心你找谁。

这个共性，决定了它的强项和天花板。强项在于：目的地信息在现行网络协议里是半公开的，获取起来几乎免费，所以这招可以大规模、全天候地使用。天花板在于：一旦目的地被藏起来——你连的地址是个平平无奇的中转，你的握手封面上写的名字也是假的或者干脆加密了——这一整套按图索骥的打法就失去了下手的地方。

请记住这个天花板，因为它就是后面梯子进化的总方向：想办法让目的地不再明牌。当然，故事要是到这里就结束，墙就太被动了。就算目的地藏起来了，流量本身还有"长相"可看——你的通信节奏、包裹大小和接通的腔调，都可能出卖你。那就是墙的第三招，也是最见功力的一招：不看你去哪，也不看你说了什么，就看你"走路的样子"像谁。

分清两种"不通"：被封门，还是被掐线

照例留一套分辨方法。封 IP 与掐连接都归墙管，但长相不同，分清了能省很多瞎折腾。

**封 IP 的长相是"人间蒸发"。** 你的请求发出去，如同寄往一个不存在的地址：没有回音、没有报错、就是等到超时为止。而且它对"换方法"免疫——你换个浏览器、换个软件，只要目的地地址不变，结果就不变；但换个目的地（比如同网站的另一台服务器），可能立刻就通了。另一个特征是"连坐":如果你发现某个公司旗下的好几个不相干的服务同时失联，多半不是它们集体故障，而是它们共用的地址段进了名单。

**掐连接的长相是"刚通话就被挂断"。** 地址是通的，手也能握上，可数据一传就断，错误信息里带着"重置""中断"之类的字眼。重试有时能撑久一点、有时立刻又被掐，很像信号不好，但换到没有审查的网络环境立刻痊愈。它的另一个签名是时机：断，总是发生在连接刚建立或刚开始传敏感内容的时候，而不是随机的任何时刻——随机断线是网络质量的毛病，卡点断线多半是有人在旁边打量。

记住这两张脸，还有一个实际用处：判断该不该花钱。节点地址被封，换节点就行，没必要换更贵的套餐；连接频繁被掐，问题可能出在通道的"长相"上，换同类型的节点再多也没用，该换的是技术类型。诊断错了，钱就花错了。

名单攻防：一场没有终点的登记战

封 IP 这一招，表面上封的是地址，实质上打的是一场"登记战"：一方的核心工作是把对方的地址摸清、登记、封存；另一方的核心工作是让地址足够多、换得足够快，或者藏在不值得封的地方。

站在节点运营者一边，应对的思路无非几条。一是勤换：地址被封了就换新地址，云服务器的地址本来就可以随开随弃，比拼的是更新速度。二是分散：一个订阅后面挂几十上百个地址，封掉一批还有一批，用户在软件里换个节点就恢复。三是借势：把节点放在大平台的地址段里，借误伤成本当护身符——前面说过，这种顾虑是真实存在的。四是保密：地址只发给付费用户、限制传播，把对方摸清地址的成本抬上去。这四条，都是在"登记战"的框架里打转，没有一条能跳出这个框架：只要你还在用"地址"这个东西做落点，你就永远在对方的名单射程之内。

站在封锁方一边，维护名单的主要成本不在封，而在"发现"。互联网上的地址以亿计，哪些正在被用作节点，不去实际侦查是不知道的。侦查的渠道也是摆在明面上的那几种：自己去把市面上的服务挨个买下来用，从中提取地址；监测出境流量，观察哪些境外地址在承接大量"长得就不正常"的连接；以及响应举报和公开信息。发现一条、登记一条，这个过程像滚雪球，所以一个节点往往不是一出生就被封，而是先活一阵子，等用户多起来、动静大起来，才被登记带走。这解释了节点死亡最典型的节奏：**不是慢慢变差，而是某天突然集体消失**。小众、低调的节点反而常常活得更久——并非它们有什么高深技术，只是在侦查的优先级里还没排到它们。

理解登记战，还有一层收获：它说明这场攻防里，"秘密"本身是一种资源。梯子圈里很多看似奇怪的现象都源于此——为什么好的服务要收费（收费墙的一大功能是防侦查）、为什么商家三令五申不许分享订阅（一次泄露等于地址全网广播）、为什么"人人都在用的免费节点"听着最诱人却死得最快。用原理的眼光看，这些都不是商家的脾气，而是这场登记战里的必然规定动作。

这一章的结论

第二招就讲到这里。它的两件兵器：封 IP 是名单制的封门，简单、确定，但怕地址变化、怕误伤合租户；掐连接靠伪造 RST，专杀正在进行的通话，在内容明文的时代还能按关键词精细下手，如今主要配合 SNI 这种"看封面"的办法使用。它们共同的命门是：必须先看清目的地。

一个自然的推论是：梯子的进化，会沿着"不让对方看清目的地"的方向展开——地址要藏，封面上的名字也要藏。但在藏无可藏之后，还剩下最后一个问题：当目的地和内容都看不见时，守关口的人是不是就束手无策了？完全不是。你的流量还有形状、节奏和腔调。下一章，墙的第三招登场：它不看内容、不认地址，它认"人"。

把前两招串成一个晚上

为了让你看到这些机制在现实里是怎么配合的，我们把前两章和这一章的招数，放进同一个晚上的故事里。主人公还是你，工具是一款普通的梯子软件，里面有一批节点。

八点整，你打开软件，连上节点 A。用隧道问路，名字没被抢答；目的地的真地址藏在隧道里，边界上只看得见你和节点 A 在通信。一切正常，视频流畅。这是梯子把前两招都防住了的理想状态。

八点四十，你正看着，画面突然冻住，重连、超时、再重连、再超时。你退出软件重进，节点 A 依然没反应。你换到节点 B，立刻满血复活。刚才发生了什么？最可能的故事是：A 的地址在这段时间里被登记进了名单。不是你的软件坏了，也不是 A 的服务器宕机——是它在边界上被"点名"了。从这一刻起，所有去往 A 的包裹都在关口被扣下，表现就是教科书式的封 IP 长相：人间蒸发，换软件没用，换地址立刻好。

九点半，你想起来要查一个资料站。这个站不在任何封禁名单里，你的梯子也开着，可它就是打不开，而别的站都好好的。你关掉梯子直连再试——还是不行。这次的嫌疑人是 SNI：这个站和某个被禁的服务共用同一个地址（合租），或者它在握手封面上露出的名字命中了某条规则，连接在你和它打招呼的那一瞬间被掐了。你能看见地址、能敲开门，唯独握手那一秒总被一张伪造的挂断条子打断。这是掐连接的标准长相。

十一点，你躺下刷手机，顺手回想今晚这一出：如果只用前两章的知识，你只会得出"网络不稳定"的结论，然后考虑换一家更贵的服务。但现在你能把故障拆成三笔账：哪笔是问路的账，哪笔是地址的账，哪笔是连接的账。账分清了，你的下一步动作就有了分寸——A 死了不是套餐不行，换个节点便是；查资料站打不开也不是节点的问题，是那个站的握手在裸奔。

这个故事的寓意，不在某一招有多高明，而在于：**墙的招数是成套部署的，梯子的活路也必须成套**。任何只防一招的方案，在实际使用中都会被其他招数从侧面击破。这也是为什么现代梯子最后普遍长成了"加密+伪装+多节点+隧道内问路"的全套打法——不是设计师贪心，是被这套组合拳一拳一拳打出来的。接下来要讲的第三招，会把这套打法逼向更极致的方向。
